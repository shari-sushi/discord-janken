# team_schedules: 他チームに見られないコメント（チーム内限定メモ）

> 元 issue: [#89](https://github.com/shari-sushi/discord-janken/issues/89)
> ⚠️ 本計画は暫定。仕様は 2026-06-17 に作者と確定する。
> ⛔ **ブロッカー候補（法務）あり** — 下記「要確認」を仕様確定前に必ずクリアすること。

## 目的・背景

**他チームには見られない・自チーム内だけで共有されるコメント**を残せるようにする。

現状、`schedules.note` は public read API（`GET /teams/[teamId]/schedule`）で誰でも閲覧でき、フロントでも非メンバーの閲覧者に相手チームのメモを表示している（[TeamSchedulesPage.tsx](../../my-app/app/team_schedules/_components/TeamSchedulesPage.tsx) の opponent 列）。チーム内の連絡・調整メモを他チームに見せたくない。

## ⛔ 要確認: 電気通信事業法（実装前のブロッカー候補）

ユーザー間の「クローズドなメッセージのやり取り」を媒介する機能は、日本の**電気通信事業法上の「他人の通信の媒介」**に該当し、電気通信事業の**届出（場合により登録）**が必要になる可能性がある。

- 単なる「チームの予定に付随する共有メモ（保存データ）」なら該当しない可能性が高いが、特定の相手へのプライベートメッセージ/DM的なものに発展すると該当リスクが上がる。
- 実装の方向性次第で扱いが変わるため、**仕様を固める前に総務省のガイドライン/専門家に確認する**こと。
- ※ これは法律の一般的な留意点であり、正式な法的助言ではない。

→ **「保存メモ（DMではない）」の範囲に留める**設計にすれば該当リスクを下げられる見込み。この前提を 2026-06-17 に確認する。

## 実装方針（案）

可視範囲: 自チームメンバー（`team_members` に存在する人）にのみ可視。非メンバー/相手チームの read では返さない（API レベルで除外）。

設計の分岐:

- **案A**: 既存 `note`(public) はそのまま残し、別概念「チーム内メモ」列/テーブルを追加（public/private の2層）
- **案B**: `note` 自体を非公開化し、相手には status のみ見せる

API 実装:

- read 経路でも `getSessionUserId` + `assertTeamMember` で「閲覧者が当該チームのメンバーか」を判定し、private 項目を出し分け
- public read API のレスポンス形を変える必要があるか検討（`#99` GET権限管理と統合）
