# 実行計画書: 格ゲーチーム戦 出場順同時発表コマンド

## 概要

格闘ゲームのチーム戦で、各チームの出場順（先鋒・中堅・大将など）を同時に発表するDiscordコマンドを実装する。

## 背景・目的

### 課題 (Issue #28より)

格ゲーのチーム戦では、戦略上の公平性を保つため、両チームの出場順を同時に発表する必要がある。
現状では以下の問題がある:

- 先鋒のみスタッフに伝えて残りは内緒
- エントリー時に順番を確定させる
- 手動で「せーの」で発表する必要があり、運営の手間がかかる

### 解決策

Discordボットで両チームが出場順を入力し、両方揃ったら自動的に同時発表する機能を提供する。

## 機能仕様

### コマンド

```text
/fighting-team-order format:2v2|3v3|5v5 team1_name:チーム1の名前 team2_name:チーム2の名前
```

**パラメータ:**

| パラメータ | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `format` | choice | ✅ | チーム戦の形式（2v2, 3v3, 5v5） |
| `team1_name` | string | ✅ | チーム1の名前（最大25文字） |
| `team2_name` | string | ✅ | チーム2の名前（最大25文字） |

### 操作フロー

```text
[運営がコマンド実行]
  └→ チャンネルにメッセージ投稿
      - チーム1・チーム2の名前を表示
      - 各チーム用の「出場順を入力」ボタン × 2個

[チーム1のメンバーが「チーム1 出場順を入力」ボタンをクリック]
  └→ モーダルを表示
      - 先鋒 (vanguard) のテキストフィールド
      - 次鋒 (second) のテキストフィールド（5v5のみ）
      - 中堅 (middle) のテキストフィールド（3v3, 5v5のみ）
      - 副将 (fourth) のテキストフィールド（5v5のみ）
      - 大将 (general) のテキストフィールド

[モーダルでメンバー名を入力して送信]
  └→ Redisに保存（match_id単位）
  └→ メッセージを更新
      - チーム1: ✅ 登録済み
      - チーム2の登録状況を確認
        - 両方登録済み → 両チームの出場順を公開表示
        - 片方のみ → 「チーム2の登録待ち」と表示

[両チーム登録完了時]
  └→ メッセージを更新して両チームの出場順を同時公開
      ```
      【チーム戦 出場順発表】

      🔵 チーム1の名前
      先鋒: プレイヤーA
      中堅: プレイヤーB
      大将: プレイヤーC

      🔴 チーム2の名前
      先鋒: プレイヤーX
      中堅: プレイヤーY
      大将: プレイヤーZ
      ```
  └→ 入力ボタンを無効化（または削除）
  └→ 「リセット」ボタンを表示
```

### リセット機能

```text
[運営が「リセット」ボタンをクリック]
  └→ Redisのデータを削除
  └→ メッセージを初期状態に戻す
      - 両チームとも未登録状態
      - 入力ボタンを再度有効化
```

## 技術設計

### ディレクトリ配置

```text
my-app/app/api/discord/application-command/fighting-game/teamOrder.ts
```

**決定理由:**

- LoL等を含めた「格ゲー(対戦ゲー?)」の機能として扱う
- 今後、格ゲー共通の機能を追加しやすい
- プロジェクト構造が整理され、可読性が向上

#### 備考：棄却された案

コマンドプレフィックスを`user/`にする：

- この機能は格ゲーのためではないが、`user-` とするにはゲーム特化しすぎている
- ゲームをする人がこの機能を探す際に `user-` プレフィックスを見ない可能性が高い
- 格ゲー特有の用語（先鋒・中堅・大将）を使うため、汎用性は低い

### custom_id 設計

| 用途 | custom_id | 備考 |
| --- | --- | --- |
| チーム1入力ボタン | `fighting-open-modal-team-order?match_id={id}&team=1` | |
| チーム2入力ボタン | `fighting-open-modal-team-order?match_id={id}&team=2` | |
| チーム入力モーダル(共通) | `fighting-register-team-order?match_id={id}&team={1\|2}` | |
| リセットボタン | `fighting-reset-team-order?match_id={id}` | |

※ `match_id` は uuid v4 (36文字)

### モーダル仕様

- 大将 (general): Text Input (short)

#### 3v3の場合

- 先鋒 (vanguard): Text Input (short)
- 中堅 (middle): Text Input (short)
- 大将 (general): Text Input (short)

#### 5v5の場合

- 先鋒 (vanguard): Text Input (short)
- 次鋒 (second): Text Input (short)
- 中堅 (middle): Text Input (short)

- 大将 (general): Text Input (short)

※ Discordのモーダルは最大5つのAction Rowまでなので、5v5がギリギリ

### Redis データ構造

`lol-match`と同様に、メタデータとチームデータを分割して保存する。

#### メタデータキー

**キー:** `fighting:team-order:{match_id}:meta`

**値 (JSON):**

```json
{
  "match_id": "uuid",
  "format": "3v3",
  "team1_name": "チーム赤",
  "team2_name": "チーム青",
  "channel_d": "123456789",
  "message_id": "987654321",
  "created_at": "2026-02-21T12:34:56.789Z"
}
```

#### チーム1データキー

**キー:** `fighting:team-order:{match_id}:team1`

**値 (JSON):**

```json
{
  "updated_at": "2026-02-21T12:35:10.123Z",
  "order": {
    "vanguard": "プレイヤーA",
    "middle": "プレイヤーB",
    "general": "プレイヤーC"
  }
}
```

#### チーム2データキー

**キー:** `fighting:team-order:{match_id}:team2`

**値 (JSON):**

```json
{
  "updated_at": "2026-02-21T12:35:15.456Z",
  "order": {
    "vanguard": "プレイヤーX",
    "middle": "プレイヤーY",
    "general": "プレイヤーZ"
  }
}
```

**TTL:** 24時間（86400秒）

**分割する利点:**

- チーム単位でのデータ取得・更新が効率的
- `lol-match`との一貫性が保たれる
- 将来的な機能拡張（チーム別の権限管理など）がしやすい

### レスポンス設計

| タイミング | レスポンス type | 内容 |
| --- | --- | --- |
| コマンド実行 | `4` (CHANNEL_MESSAGE_WITH_SOURCE) | 初期メッセージ + 2つの入力ボタン |
| 入力ボタン押下 | `9` (MODAL) | 出場順入力モーダル表示 |
| モーダル送信 | `7` (UPDATE_MESSAGE) | メッセージ更新（登録状況反映） |
| リセットボタン | `7` (UPDATE_MESSAGE) | メッセージを初期状態に戻す |

### ハンドラー関数

`teamOrder.ts` に以下の4つの関数を実装:

1. **`handleFightingTeamOrderCommand()`**
   - APPLICATION_COMMAND 処理
   - 初期メッセージを投稿
   - Redisに初期データを保存

2. **`handleFightingOpenModalTeamOrder()`**
   - 両チーム共通
   - `fighting-open-modal-team-order` ボタン処理
   - モーダルを表示（formatに応じた入力フィールド）

3. **`handleFightingRegisterTeamOrder()`**
   - 両チーム共通
   - モーダル送信処理
   - Redisに出場順を保存
   - 相手チームの登録状況を確認
   - 両チーム登録済みなら発表、片方なら待機メッセージ

4. **`handleFightingResetTeamOrder()`**
   - リセットボタン処理
   - Redisデータを削除
   - メッセージを初期状態に戻す

## 注意事項

### Discord制限

- **モーダル制限**: 最大5つのAction Rowまで → 5v5がギリギリ
- **custom_id制限**: 100文字まで → uuid (36文字) + クエリパラメータで十分
- **3秒制限**: Redis操作は軽量なので問題なし

### バリデーション

- **入力必須**: 各ポジションのプレイヤー名は必須入力（`required: true`）
- **重複登録**: 同じチームが複数回登録した場合は上書き（Redisの値を更新）
- **format検証**: コマンド実行時に choice で制限されるため、不正な値は来ない

### TTL設定

- **24時間**: 試合終了後も確認できるよう、1日間保持
- **リセット時**: TTLも再設定

### 用語の選択

- **日本語**: 先鋒・中堅・大将（格ゲーコミュニティで一般的）
- **英語キー**: vanguard, middle, general など（コード内）

## 実装時の設計決定

### ビジネスロジックの型定義による表現

**採用した設計:**

フォーマットごとのポジション構成を定数として型安全に定義：

```typescript
const TEAM_FORMAT_POSITIONS: Record<TeamFormat, Array<keyof TeamOrderData>> = {
  "2v2": ["vanguard", "general"],
  "3v3": ["vanguard", "middle", "general"],
  "5v5": ["vanguard", "second", "middle", "fourth", "general"],
}
```

**採用理由:**

- **ビジネスロジックの可視化**: 各フォーマットのポジション構成が一目で分かる
- **型安全性**: `Record<TeamFormat, ...>`により全フォーマットの定義が強制される
- **DRY原則**: モーダル生成(`createTeamOrderModal`)とメッセージ整形(`formatTeamOrder`)で同じロジックを共有
- **保守性**: 新フォーマット追加時は1行追加するだけ
- **条件分岐の削減**: 各関数内で`format === "5v5"`のような条件分岐が不要

**効果:**

- `createTeamOrderModal`: 条件分岐4回+push5回 → `map`1回で一括生成
- `formatTeamOrder`: 条件分岐4回+push5回 → `map`1回で一括生成
