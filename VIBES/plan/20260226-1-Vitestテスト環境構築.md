# Vitestテスト環境構築実行計画

## 目的

issue #36「テストちゃんとする」に対応し、プロジェクトにVitestベースのテスト環境を構築する。

## 背景

### issue #36の要約

- **現状**: 実験的実装として開始したため、テストが存在しない
- **課題**: 実際に利用され始め、複雑度が増すと共にデプロイ時にバグが無いことの重要度が増した
- **目標**: 開発速度を加速するためのテスト環境整備

また、実装が進むこと適切なテスト実装方法が明確になってきたたことで本計画に至った。

### テスト要件

1. **テストフレームワーク**: Vitest
2. **テスト種別**:
   - 単体テスト: 複雑な純関数やバリデーション結果が難しいもの
   - 統合テスト: 全Web APIエンドポイント、Discord bot API
3. **テスト方針**:
   - 正常系・異常系・境界値・限界値のテスト
   - GitHub workflow統合（PRでのコンパイルエラーチェック・テスト実行）
   - 変更されたディレクトリのテストのみ実行（例: `my-app/app/api/discord`）
4. **開発思想**:
   - 100%カバレッジではなく、開発速度の加速を重視  
    $
    開発速度の加速　　　 = やりたいことに注力し、やりたくないことを最小限で済ますこと \\
    やりたいこと　　　　 = 機能実装 + 運用  \\
    やりたくないこと１　 = テスト実装 + 要件変更によるテスト修正 \\
    やりたくないこと２　 = デバッグ + トラブル対応 + トラブル対応割り込みによるコンテキストスイッチの発生
    $
   - API層の統合テストは必ず行う(must) ← これがこのアプリを保証する
   - 単体テストは複雑なものに絞って行うべき(should) ← 補助的立場

## テスト戦略

### レベル別テスト方針

| テストレベル | 対象 | 配置場所 | 優先度 |
| ------------ | ------ | --------- | ------- |
| 統合テスト | Web API全エンドポイント、Discord bot API | `__tests__/integration/` | 高 |
| 単体テスト | 複雑なユーティリティ関数、バリデーション | ソースと同じディレクトリ | 中 |
| E2E | Discord UI（やり方募集中） | 未定 | 低(今回は無し) |

### 統合テストで検出できるバグ（重要）

Discord APIの統合テストは、単なる「レスポンスタイプの確認」ではなく、**実際の運用で発生するバグを検出**するために実施する。

#### 検出できる具体的なバグ例

1. **custom_idの生成ミス**
   - 例：`protect_blue_team_${matchId}` のmatchIdが正しく埋め込まれていない、その他keyの不整合
   - 影響：ボタンクリック時にモーダルが開かない、または別の試合のデータを編集してしまう

2. **matchIdの受け渡しエラー**
   - 例：コマンド → ボタン → モーダル の各段階でmatchIdが消失・変化
   - 影響：データが保存されない、または間違った試合に保存される

3. **モーダルの構造ミス**
   - 例：Action Rowの数が6個（上限5個を超過）
   - 例：TextInputのlabelが抜けている
   - 影響：Discord側でエラーが発生し、モーダルが表示されない

4. **Redisキーの命名ミス**
   - 例：`protect:{matchId}:blue_team` と `protect:{matchId}:blueteam` の不一致
   - 影響：データが保存されても読み取れない

5. **データの保存漏れ**
   - 例：モーダル送信後、Redisへの保存処理が実行されていない
   - 影響：ユーザーは成功メッセージを見るが、実際にはデータが保存されていない

#### テストアプローチ

```typescript
// ❌ 意味のないテスト（うわべだけの保証。コードレビューでまず見落とさないこと。）
test('プロテクトボタンがモーダルを返す', () => {
  const result = handleProtectButton(mockPayload);
  expect(result.type).toBe(9); // MODAL
});

// ✅ 意味のあるテスト（実際のフローとデータを検証、操作回数が多く手動デバッグでの網羅が難しいもの）
test('プロテクト機能の完全フロー', async () => {
  // ① コマンド実行 → ボタン付きメッセージを返す
  const cmdResponse = await POST(mockProtectCommand);
  expect(cmdResponse.data.components).toContainButtonWith('protect_blue_team');

  const matchId = extractMatchId(cmdResponse);

  // ② ボタンクリック → 正しいmatchIdを含むモーダルを返す
  const btnResponse = await POST(mockButtonClick(matchId));
  expect(btnResponse.data.custom_id).toBe(`protect_modal_blue_${matchId}`);

  // ③ モーダル送信 → Redisに正しく保存される
  await POST(mockModalSubmit(matchId, 'Ahri'));
  const saved = await redis.get(`protect:${matchId}:blue_team`);
  expect(saved).toBe('Ahri');
});
```

### テスト実行戦略

- **開発時**: `npm run test:watch` で変更ファイルの自動テスト
- **PR時**: GitHub Actionsで全テスト実行
- **最適化**: 変更されたディレクトリのテストのみ実行

### 設計原則

1. **コロケーション原則**: 単体テストはソースファイルと同じ場所に配置
2. **統合テストの分離**: `__tests__/integration/` に集約
3. **共通リソースの共有化**: `__tests__/helpers/` と `__tests__/mocks/`
4. **命名規則**:
   - 単体テスト: `*.test.ts`
   - 統合テスト: `*.integration.test.ts`

**方針**: 単純なハンドラー関数の単体テストは行わない（統合テストでカバー）

- 単純なレスポンス生成ロジックをテストしても意味がない

- メンテナンスコストが無駄

## 注意点

### 1. テストカバレッジの考え方

- **目標**: 開発速度の加速（100%カバレッジではない）
- **重点**: API層の統合テスト - **実際のバグを検出できるテスト**
- **最小限**: 単体テストは複雑なロジックのみ
- **避ける**: 実装をなぞるだけの無意味なテスト

#### 統合テストに集中する理由

| テストタイプ | 検出できるバグ | コスト | 投資対効果 |
| ------------ | -------------- | ------- | ---------- |
| 統合テスト（コマンド→ボタン→モーダル→保存） | custom_id生成ミス、matchId受け渡しエラー、Redis保存漏れ | 中 | **高** |
| 単体テスト（複雑なロジック） | アルゴリズムのバグ | 低 | 高 |
| 単体テスト（ハンドラー関数個別） | なし（実装をなぞるだけ） | 低 | **低** |

### 2. モック戦略

- **Redisモック**: `vi.mock()` で完全モック化
  - テスト環境でも実際の保存・取得動作を再現
  - テスト後は自動クリーンアップ
- **Discord署名検証**: テスト環境では無効化
  - `process.env.NODE_ENV === 'test'` で分岐
- **外部API**: 全てモック化（Google Sheets等）
  - 実際のAPIを叩かない（速度・安定性）

### 3. テスト実行の最適化

- **ウォッチモード**: 開発時は変更ファイル関連のみ実行
- **並列実行**: 可能な限り並列実行で高速化
- **CI/CD**: 変更されたディレクトリのテストのみ実行

### 4. Discord UI テストの課題

- **課題**: Discord UIの検証は困難（自動化ライブラリが存在しない）
- **現状**: APIレベルの統合テストで代替
  - HTTPリクエスト/レスポンスのテスト
  - Redisデータの検証
- **将来**: 適切なライブラリが見つかれば導入検討

### 5. TDD（テスト駆動開発）の導入

- **将来的な方針**: 要件が明確な新機能はTDDで開発
  - Red-Green-Refactorサイクルの実践
  - テストを先に書いてから実装する
- **現状**: 既存コードには後からテストを追加
- **段階的移行**: Phase 2以降の新機能開発からTDDを適用

### 6. 無意味なテストを書かない

❌ **避けるべきテストパターン**:

```typescript
// 実装をなぞるだけ - 意味がない
test('ボタンがモーダルを返す', () => {
  const result = handleButton(mock);
  expect(result.type).toBe(9); // これだけ？
});
```

✅ **価値のあるテストパターン**:

```typescript
// 完全なフローとデータを検証 - バグを検出できる
test('プロテクト機能が正しく動作する', async () => {
  const cmd = await POST(mockCommand);
  const matchId = extract(cmd);

  const btn = await POST(mockButton(matchId));
  expect(btn.data.custom_id).toContain(matchId); // matchId引き継ぎ確認

  await POST(mockModal(matchId, 'Ahri'));
  const saved = await redis.get(`protect:${matchId}:blue_team`);
  expect(saved).toBe('Ahri'); // 実際にデータが保存されたか確認
});
```

**判断基準**: 「このテストが失敗したら、実際のバグを見つけられるか？」
- YES → 書く価値がある
- NO → 書かない
