# REST API実装：プロテクトメッセージ送信機能

## 📋 背景と目的

### 要件

- Discord bot コマンド `/lol-new-protect` と同じ結果をREST APIから実現したい
- 指定したDiscordサーバー（guild）のチャンネルに、ボット自身がプロテクト登録用のメッセージを送信する
- REST API の引数として `guild_id` と `channel_id` を受け取る

### 目的

1. **外部システムからの連携を可能にする**：Discordコマンド以外の方法でプロテクト機能を開始できるようにする
2. **自動化の基盤を作る**：将来的にスケジューラーや他のシステムからの自動トリガーを可能にする
3. **柔軟性の向上**：Discordのスラッシュコマンド以外のトリガーポイントを提供

---

## 🎯 実装方針

### 採用するアプローチ

**Discord REST API を利用したメッセージ送信**

既存の `/lol-new-protect` コマンドは、Discordからのインタラクションに対する「レスポンス」として動作します。
一方、今回作成するREST APIは、Discord Bot Token を使用してDiscord REST APIに直接メッセージを送信する「能動的な送信」となります。

### URL設計

**エンドポイント**: `POST /api/web/lol/matches`

#### リソース設計の考え方

試合（match）を親リソースとして扱います。

- 試合のセッティング（作成）と、プロテクト機能は本来別の操作
- 試合に紐づく各種情報（プロテクト、結果、メンバー等）を階層構造で管理

#### 本来のRESTful設計 vs 今回の実装

**本来のRESTful設計**:

```txt
1. POST /api/web/lol/matches
   → match_id を取得

2. POST /api/web/lol/matches/{match_id}/protect
   → プロテクト機能を開始
```

**今回の実装（I/O削減のため）**:

```txt
POST /api/web/lol/matches { isProtect: true }
→ 試合作成とプロテクト開始を同時に実行
```

- `isProtect: true` の場合: 試合作成 + Discordにプロテクト登録メッセージ送信
- `isProtect: false` の場合: 何もしない（将来拡張用として引数のみ用意）
- I/O回数を削減するための実装上の最適化

#### 設計理由

1. **RESTful設計**: URLはリソース（`matches`）を表し、HTTPメソッド（`POST`）が操作（試合作成）を表す
2. **階層構造の明確化**: 試合を親リソースとし、関連情報を子リソースとして扱う
3. **拡張性の確保**: 試合に関連する情報を自然に追加できる構造

#### リソース階層

```txt: イメージ(将来像)
Match (試合) - /api/web/lol/matches
  ├── protect (プロテクト情報) - /api/web/lol/matches/:match_id/protect
  ├── join (試合に参加希望を表明) - /api/web/lol/matches/:match_id/join
  ├── members (参加メンバー) - /api/web/lol/matches/:match_id/members
  └── result (試合結果) - /api/web/lol/matches/:match_id/result
```

#### メリット

- **URLから関係性が明確**: `/matches/:match_id/protect` で試合とプロテクト情報の関連が分かる
- **将来的な拡張が容易**: その試合にまつわる色々な拡張が自然に追加できる
- **標準的なREST設計**: 親子リソースの関係を表現する一般的なパターン
- **実装の整理**: ディレクトリ構造とURLが対応し、保守しやすい

#### Discord botコマンドとの関係

- **Discord側**: ユーザーにとって分かりやすいコマンド名
- **REST API側**: リソース指向の設計 + `isProtect` フラグで動作を制御
- `/lol-new-protect` は `POST /matches { isProtect: true }` に相当


```txt
Discord bot:
  /lol-new-protect → レスポンスで「新しいプロテクトの開始UI」を表示

Web API:
  POST /api/web/lol/matches { isProtect: true }
  → 「試合リソースを作成」+ discord botにメッセージを投稿させて「新しいプロテクトの開始UI」を表示
```



### アーキテクチャ

```txt
外部システム/ユーザー
    ↓ POST /api/web/lol/matches
    ↓ {guild_id, channel_id, isProtect}
Next.js API
    ↓ セッション認証
    ↓ パラメータ検証
    ↓ match_id生成
    ↓
    ↓ isProtect === true ?
    ├─ Yes → Discord REST API呼び出し
    │         ↓ POST https://discord.com/api/v10/channels/{channel_id}/messages
    │         ↓ Authorization: Bot {DISCORD_BOT_TOKEN}
    │       Discord Server
    │         ↓ メッセージが指定チャンネルに送信される
    │         ↓ ボタン（青チーム・赤チーム・確認）付き
    │       ユーザーがボタンをクリック
    │         ↓ 既存の `/api/discord/route.ts` で処理
    │
    └─ No → 400 Bad Request エラーを返却（将来拡張用）
```

## 📦 詳細な実装内容

### 1. 新しいAPIエンドポイントの作成

**ファイル**: `my-app/app/api/web/lol/matches/route.ts`

#### 機能

- HTTPメソッド: POST
- 認証: Bearer token（既存のセッション認証を使用）
- リクエストボディ:

  ```json
  {
    "guild_id": "1234567890123456789",
    "channel_id": "9876543210987654321",
    "isProtect": true
  }
  ```

  パラメータ説明:
  - `guild_id`: Discord サーバーID
  - `channel_id`: Discord チャンネルID
  - `isProtect`?: プロテクト機能を開始するか（boolean）
    - `true`: 試合作成 + プロテクト登録メッセージをDiscordに送信
    - `false`: 何もしない（将来拡張用として引数のみ用意）
    - undedined: falseとして扱う

- レスポンス（成功時、`isProtect: true`）:

  ```json
  {
    "success": true,
    "match_id": "uuid-generated-match-id",
    "message_id": "1111222233334444555"
  }
  ```

- レスポンス（`isProtect: false` の場合）:

  ```json
  {
    "success": false,
    "error": "isProtect: false は現在サポートされていません（将来拡張用）"
  }
  ```

  HTTPステータス: 400 Bad Request

- レスポンス（エラー時）:

  ```json
  {
    "success": false,
    "error": "エラーメッセージ"
  }
  ```

#### 処理フロー

1. セッション認証（Bearer token）
2. リクエストボディのバリデーション（guild_id, channel_id, isProtect の存在確認）
3. **isProtect フラグによる条件分岐**:
   - `isProtect === false` の場合:
     - `// note: isProtect: false は将来拡張用。現在は何もせずエラーを返す` とコメント
     - 400 Bad Request エラーを返して終了
   - `isProtect === true` の場合:
     - 試合ID（matchId）の生成
     - Discord REST API用のメッセージペイロード作成
     - Discord API へのPOSTリクエスト送信
     - レスポンスに match_id と message_id を含める
4. レスポンスの返却

### 2. Discord API通信用ヘルパー関数の作成

**ファイル**: `my-app/app/libs/discordApi.ts`

#### 関数

```typescript
/**
 * Discordチャンネルにメッセージを送信する
 * @param channelId - 送信先のチャンネルID
 * @param content - メッセージ本文
 * @param components - ボタンなどのコンポーネント配列
 * @returns Discord APIからのレスポンス（message_id等）
 */
export async function sendDiscordMessage(
  channelId: string,
  content: string,
  components?: any[]
): Promise<DiscordMessageResponse>
```

#### 実装詳細

- Discord REST API v10 を使用
- エンドポイント: `https://discord.com/api/v10/channels/{channel_id}/messages`
- ヘッダー:
  - `Authorization: Bot ${DISCORD_BOT_TOKEN}`
  - `Content-Type: application/json`
- エラーハンドリング:
  - 401 Unauthorized: Bot tokenが無効
  - 403 Forbidden: チャンネルへの送信権限がない
  - 404 Not Found: チャンネルが存在しない
  - 429 Too Many Requests: レート制限

### 3. メッセージコンポーネントの共通化

**ファイル**: `my-app/app/util/protectMessageComponents.ts`

#### 目的

`newProtect.ts` と新しいREST APIで同じメッセージ構造を使い回すために、コンポーネント生成ロジックを共通化

#### 関数

```typescript

 * プロテクト機能用のボタンコンポーネントを生成

 * @returns Discordコンポーネント配列
```

#### 変更が必要な既存ファイル

- `my-app/app/api/discord/application-command/newProtect.ts`
  - `newProtectCommand()` 関数内のコンポーネント生成部分を、新しい共通関数を使用するように変更

### 4. 環境変数の確認

**必要な環境変数**:

- `DISCORD_BOT_TOKEN`: 既存で使用されているはずだが、念のため確認

### 5. バリデーション関数の作成

**ファイル**: `my-app/app/api/web/lol/_validators/discordValidators.ts`

#### 関数

```typescript
/**
 * Discord ID（guild_id, channel_id等）のフォーマットを検証
 * @param id - 検証対象のID
 * @returns バリデーション結果
 */
```

#### 検証内容

**validateDiscordId()** - Discord ID（guild_id, channel_id）の検証:

- 文字列型であること
- 空文字列でないこと
- 17-19桁の数値文字列であること（Snowflake ID形式）

**追加の検証** - isProtect パラメータの検証:

- boolean型であること

## ⚠️ 注意事項

### セキュリティ

1. **認証の必須化**: REST APIは必ずセッション認証を通すこと
2. **guild_id の検証**: （オプション）ボットが参加しているサーバーかどうかを確認することも検討
3. **レート制限への対応**: Discord APIのレート制限に注意

### Discord APIの制約

1. **Bot権限**: ボットが対象チャンネルへのメッセージ送信権限を持っている必要がある
2. **チャンネルタイプ**: テキストチャンネルのみ対応（音声チャンネルには送信不可）
3. **Snowflake ID**: guild_id と channel_id はDiscord固有のSnowflake ID形式

### 既存機能への影響

- `newProtect.ts` の修正により、既存の `/lol-new-protect` コマンドの動作が変わらないことを確認する
- コンポーネント構造を変更する場合、`route.ts` のハンドラーも影響を受ける可能性があるため注意

### 設計上の注意

1. **試合作成とプロテクトは本来別の操作**
   - 本来のRESTful設計では `POST /matches` → `POST /matches/:id/protect` の2段階
   - 今回は I/O 削減のため `isProtect` フラグで同時実行
   - この設計判断を理解した上で実装すること

2. **isProtect: false の実装**
   - 現時点では何もせず400エラーを返す（試合作成もしない）
   - コード上に `// note:` コメントで将来拡張予定を明記すること
   - 将来的には試合情報のDB保存などを実装予定

## 🧪 テストシナリオ

### 正常系

1. `isProtect: true` で有効な認証トークン、guild_id、channel_id でAPIを呼び出し
   - → 200 OK、メッセージがDiscordチャンネルに送信される
   - レスポンスに match_id と message_id が含まれる

2. 送信されたメッセージのボタンをクリック
   - → 既存の処理（モーダル表示、登録、確認）が正常に動作する

3. `isProtect: false` で有効な認証トークン、guild_id、channel_id でAPIを呼び出し
   - → 400 Bad Request、Discordにメッセージは送信されない
   - エラーメッセージ「isProtect: false は現在サポートされていません（将来拡張用）」

### 異常系

1. 認証トークンなしでAPIを呼び出し
   - → 401 Unauthorized

2. 無効な guild_id / channel_id
   - → 400 Bad Request（バリデーションエラー）

3. isProtect パラメータが欠落、または boolean 以外の値
   - → 400 Bad Request（バリデーションエラー）

4. `isProtect: true` で存在しないチャンネルIDを指定
   - → Discord APIから404エラーが返り、適切にハンドリングされる

5. `isProtect: true` でボットが参加していないサーバーのチャンネルIDを指定
   - → Discord APIから403エラーが返り、適切にハンドリングされる
