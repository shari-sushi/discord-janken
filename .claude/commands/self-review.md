# セルフレビュー

現在の変更を、過去に受けた指摘を繰り返さない観点でセルフレビューする。
補足（あれば）: $ARGUMENTS

## 進め方

### 1. レビュー対象の差分を把握する

- `git branch --show-current` で作業ブランチを確認（意図したブランチか）
- `git --no-pager diff main...HEAD` と `git --no-pager status -sb` で、コミット済み + 未コミットの両方を対象にする
- PR がある場合は `gh pr view` で説明文も読む（後述の「明文化チェック」で使う）

### 2. 蓄積された教訓を読み込む

レビュー前に必ず以下を読み、観点に加える:

- `.claude/feedback/log.md`（過去に受けた個別の指摘）
- `.claude/feedback/lessons.md`（蒸留済みの教訓）

### 3. fresh-eyes でレビューする（重要）

**コードを書いた文脈のまま自己レビューすると同じ思い込みを持ち越して見逃す。**
変更が自分の手によるものなら、`Agent`（`code-reviewer` 等のレビュー用、無ければ `Explore`）に**クリーンな文脈で**差分レビューを依頼し、その指摘を取り込む。差分が小さい/自明な場合のみ自分で実施してよい。

### 4. チェックリスト

過去の指摘から特に以下を重点的に見る（log.md の蓄積に応じて随時追加）:

- [ ] **値と型のソース一致**: enum 値を代入するフィールドの型注釈が、生の `number`/`string` ではなく元の enum 型になっているか（例: `flags?: number` ではなく `flags?: MessageFlags`）。値と型の出所が食い違っていないか。
- [ ] **既存パターンとの一貫性**: 同種の処理が既にある場合、その流儀（defer の有無・エラーハンドリング・型定義の置き場所）に揃っているか。
- [ ] **correctness**: 分岐の網羅、失敗時の挙動、非同期処理（`after`/Promise）の順序と例外伝播。
- [ ] **共有 state の書き手を全部数える**: ある state（キャッシュ・`schedulesByTeam` 等）を**新たに再取得／上書きする**変更を入れたら、その state を書く**他の経路**（楽観更新、fire-and-forget の保存、別 effect・別ハンドラ）を列挙し、競合（未確定の書き込みを後着の上書きが潰す等）を点検する。fetch 対 fetch だけでなく fetch 対 ローカル編集も脅威モデルに入れる（PR #189 指摘1）。
- [ ] **「後で回復/再実行する」の主張はトリガを裏取り**: コメントや握りつぶしの根拠に「次の○○で再取得される／回復する」と書くなら、その再実行を起こす具体的トリガ（どの dep 変化・どのイベント）が実在するか確認する。安定参照の deps では effect は自発再実行しない（PR #189 指摘2）。
- [ ] **同じ不変条件の二重実装**: 非自明な不変条件（「より広いときだけ適用」等）が2箇所以上に現れたらヘルパーへ集約する。自分の修正で既存ロジックを手書きコピーしていないか、「直した結果」にも一貫性 lens を当てる（PR #189 指摘3）。
- [ ] **規約**: `.claude/rules/coding-standards.md` 準拠。テストがあれば `success:`/`failure:` プレフィックス。
- [ ] **lint / 型**: `cd my-app && npm run lint` と `npx tsc --noEmit` が通るか（コーディング終了時の必須項目）。

### 5. 「明文化」チェック（不要な再指摘を防ぐ）

実装時にあえて選んだトレードオフ（処理順序・設計の非対称・あえて修正しなかった既知のリスク等）を洗い出し、
**その根拠が PR 説明文 or コードコメントに書かれているか**を確認する。書かれていなければ追記を提案する。
→ 検討済みの判断を明文化しておけば、レビューアが settled な事項を再指摘するコストを防げる。

## 出力

以下の形式でまとめる:

- **must（マージ前に直すべき）**: バグ・規約違反・型不整合など
- **nice-to-have（任意改善）**: 各項目に自分の推奨（直す/現状維持）と理由を添える
- **明文化すべき判断**: PR 説明 or コメントに追記を提案する項目
- **lint / tsc 結果**

指摘が新種のパターンで、今後も繰り返しそうなら `.claude/feedback/log.md` への追記も提案すること。
