## 2026-06-17: セルフレビューで型の不整合を見逃し、設定済みのトレードオフを再指摘された

**カテゴリ**: process
**状況**: PR #124（team-schedule-invite の defer 化）をセルフレビューして「問題なし」とした後、別セッションのレビューで指摘を受けた。

**ミス（2種類）**:

1. **見逃すべきでなかった指摘**: `createFollowupMessage` で値は `MessageFlags.Ephemeral`（enum）を代入しているのに、入れ物の型は `flags?: number` と生のプリミティブにしていた。値と型のソースが食い違う不整合で、セルフレビューで気づけたはずなのに見逃した。
2. **させずに済んだ指摘**: 「safeEdit の失敗順序」「1チーム時に2メッセージになる非対称」など、自分では実装時に検討して妥当と判断していたトレードオフを、レビューアが（記録が無いため）改めて指摘してきた。レビュー往復のコストになった。

**正解**:

1. **値の出所＝型にする**: enum 値を代入するフィールドは、型注釈も同じ enum（`MessageFlags`）にする。`number` への暗黙の広がりは不整合のサイン。セルフレビュー時に「値と型のソースが一致しているか」を1項目として見る。
2. **判断の根拠を見える場所に残す**: 検討済みのトレードオフ（あえてこの順序/この設計にした理由）は、PR 説明文 or コードコメントに先回りで書く。書いておけばレビューアは settled として再指摘しない。「指摘されそうなこと」は脳内で潰すのではなく明文化する。
3. **コンテキストを変えてセルフレビューする**: コードを書いた同じ文脈のまま自己レビューすると、同じ思い込み（例: 上記の型不整合）を持ち越して見逃す。fresh-eyes パス（別エージェント/クリーンな文脈でのレビュー）を挟むと、型・一貫性の機械的な抜けを拾える。

## 2026-06-17: コメントが外部APIの実挙動と食い違っていた（#112 / PR #123） [distilled]

**カテゴリ**: code-quality
**状況**: team_schedules の比較チーム選択を localStorage 永続化。初期ロード後に「存在しないチームの選択を除去する」reconcile を実装し、コメントを付けた。
**ミス**: コメントに「削除・**権限喪失**で存在しなくなったチームを除去」と書いた。だが `GET /team-schedules/teams` は WHERE 無しで**全チームを public read** で返す（teams/route.ts）。よって権限喪失では選択は消えず、実際に消えるのは DB 削除されたチームのみ。コメントが実挙動と不一致だった（実害なし・ドキュメント誤り）。
**正解**: コメントで外部モジュール（API・認証フロー）の挙動に言及するときは、その挙動を**当該コードを読んで裏取り**してから書く。今回なら teams API に WHERE が無い（public read）ことを確認すれば「権限喪失」が誤りと分かった。
**なぜセルフレビューで見つからなかったか**: セルフレビューは diff **内部**の論理（無限ループ防止・依存配列・ハイドレーション）は検証したが、diff の**外**にあるAPI契約を確認しなかった。コメントの主張を「自分の思い込み（=非メンバーは見えないだろう）」のまま通し、データ源の semantics を読みに行かなかった。

## 2026-06-17: モジュールグローバルなキャッシュの寿命を「性能/UX」視点だけで評価した（#112 / PR #123）

**カテゴリ**: design
**状況**: `_selectionStore.ts` で useSyncExternalStore 用に module-level `cache` を持たせた。
**ミス**: cache が SPA セッション中ずっと残る点を「リロードを挟まず再訪しても選択が保たれる利点」とだけ捉え、**ユーザーA ログアウト→ユーザーB ログイン（リロード無し）で前ユーザーの選択が残り得る**という別ユーザー混入の観点を検討しなかった（低リスクだが未検討）。
**正解**: module-level の可変状態を置くときは「いつ初期化/破棄されるか」を**アイデンティティ変更（ログアウト/ログイン）やマルチタブの観点**でも評価する。
**なぜセルフレビューで見つからなかったか**: グローバル状態の寿命を単一ユーザーのハッピーパスでしか想定せず、セッション/アイデンティティが切り替わる脅威モデルを列挙しなかった。「便利（=残る）」と評価した時点で、同じ性質が「危険（=残る）」にもなる両面性に気づけなかった。

## 2026-06-17: useCallback の deps に searchParams を入れ、effect 再実行リスクを作った（#134） [distilled]

**カテゴリ**: code-quality
**状況**: team_schedules で token/join のURL掃除時に team= を残すヘルパー `cleanUrlKeepingTeam` を `useCallback` で作り、`searchParams` を deps に入れた。そのヘルパーを `?token=` / `?join=` の useEffect の依存配列に含めた。
**ミス**: `useSearchParams()` の戻り値はクエリ変更時に同一性が変わるため、`cleanUrlKeepingTeam` の参照も変わり、依存する effect が再実行され得る。特に verifyMagicLink を含む token effect が pending 中に再実行されると二重呼び出しになる。既存コードは `token`/`joinToken` を**文字列に落として** deps にしており（searchParams オブジェクトを避ける流儀）、そこと不一致だった。
**正解**: effect/コールバックの deps には searchParams オブジェクトそのものを入れない。(1) 必要な値は文字列に派生させて deps にする、(2) 掃除系コールバックは呼び出し時点で `window.location.search` を読み、deps は安定参照（router）だけにする。「ガードフラグ(ref)」も、`router.replace` でクエリが消えれば次回 early-return する設計なら不要。
**なぜセルフレビューで見つからなかったか**: 自分の差分内（team= を残すロジック）の正しさは確認したが、**既存 effect の deps 設計の流儀（searchParams を避け文字列派生する）に揃っているか**という一貫性チェックを飛ばした。fresh-eyes エージェントが既存パターンとの差分として拾った。

## 2026-06-18: 検討済みトレードオフの明文化漏れで再び再指摘された（PR #138 / #126）

**カテゴリ**: process
**状況**: PR #138（チーム管理画面・team 部分更新 PATCH）を別セッションがレビュー。fresh-eyes セルフレビューを2回通した後だった。
**ミス**: route の (a)「UPDATE 後に別 SELECT で返す（`.returning()` で1往復に畳まず、no-op パスと返却ロジックを1箇所に揃える意図）」、(b)「`const result: TeamSummary = team` はコンパイル時アサーション（`POST /teams` と同流儀）」という、実装時に意図して選んだ2点を**コメントに残していなかった**ため、低優先指摘として挙がった（いずれも修正不要と判断し、コメント追記で対応）。2026-06-17 の process エントリ「判断の根拠を見える場所に残す」と**同じ失敗の再発**。
**正解**: 「レビュアーが目を留めそうな非自明な実装選択」は、自分で妥当と判断していてもその場でコメント化する。特に再指摘されやすい3類型 ——(a) 1往復に畳めるのにあえて畳まない、(b) 一見冗長な型アサーション、(c) 既存別ファイルの流儀に合わせた—— はコミット前に「この非自明行、なぜこう書いたかの説明がコードに在るか」を必ず通す。
**なぜセルフレビューで見つからなかったか**: 2回の fresh-eyes でも観点が「正しさ（correctness/型/一貫性）」に寄っており、「正しいが非自明＝説明が要る箇所」を洗い出すパスを独立に回していなかった。正しさの検証と「再指摘されないための明文化」は別作業。

## 2026-06-18: 状態の正しさは検証したが、状態遷移のユーザー影響（UX）を評価しなかった（PR #138 / #126）

**カテゴリ**: ux
**状況**: 管理モード members⇄team 切替機能。保存後に自チームを再取得して全セル差し替え（＝モード不一致で全セル未記入になる罠の回避）まで作り込んだ。
**ミス**: members→team 切替で各メンバーの個別予定が画面から消える（孤児化）副作用について、操作する管理者への**注意書きが無かった**。レビューで「切替の結果を予測できず誤操作の不安」を指摘され、select 直下に注意書き（データは保持される旨込み）を追加した。
**正解**: 状態遷移を伴う操作は「データの正しさ」だけでなく「操作後に画面がどう変わるかをユーザーが事前に予測できるか」を1観点として評価する。表示が大きく変わる/消えるトグルには、その場に副作用の一文（安心材料込み）を添える。
**なぜセルフレビューで見つからなかったか**: レビュー観点が correctness/型/一貫性に寄り、「実際の利用者が操作した時の体験」を想像する UX 観点が抜けていた。grid が空になる罠は“技術的整合”としては潰した（再取得）が、“ユーザーが意図通りに感じるか”という上位の問いに接続しなかった。

## 2026-06-18: コメント内の具体値（Tailwind 透過度）が実コードと食い違い、蒸留済みパターンが再発（PR #137）

**カテゴリ**: code-quality
**状況**: PR #137 のコメントレビュー中、team列○強調のコメントに「○の強調 bg は半透明（成立行の背景 emerald/30 と**同種**）」とあった。実値は強調 `bg-emerald-900/40`、成立行は `bg-emerald-900/30`。
**ミス**: コメントが具体的な数値（`/30`）に言及しているのに、実際に適用している値（`/40`）と一致していなかった。`53-59行目で同 PR のコメント不正確を蒸留した直後の再発`で、しかも fresh-eyes セルフレビュー済み（PR 説明で「裏取り済み」と記載）をすり抜けた。
**正解**: コメントが**具体値（クラス名・数値・しきい値・色トークン）に言及するなら、その値を実コードからコピペで一致させる**。「同種」「程度」のような曖昧語でも、引き合いに出す対象（成立行/詰み行）の値を開いて照合する。値に言及しないなら数値を書かない方が安全（「行背景と近い半透明」で十分）。
**なぜセルフレビューで見つからなかったか**: コメントは「散文」として読み流し、コード本文ほど厳密に値照合していなかった。correctness パスは実装ロジックの値（`opp:teamId` 等）は照合したが、コメント中の装飾的な具体値は検証対象に入れていなかった。
