## 2026-06-17: セルフレビューで型の不整合を見逃し、設定済みのトレードオフを再指摘された

**カテゴリ**: process
**状況**: PR #124（team-schedule-invite の defer 化）をセルフレビューして「問題なし」とした後、別セッションのレビューで指摘を受けた。

**ミス（2種類）**:

1. **見逃すべきでなかった指摘**: `createFollowupMessage` で値は `MessageFlags.Ephemeral`（enum）を代入しているのに、入れ物の型は `flags?: number` と生のプリミティブにしていた。値と型のソースが食い違う不整合で、セルフレビューで気づけたはずなのに見逃した。
2. **させずに済んだ指摘**: 「safeEdit の失敗順序」「1チーム時に2メッセージになる非対称」など、自分では実装時に検討して妥当と判断していたトレードオフを、レビューアが（記録が無いため）改めて指摘してきた。レビュー往復のコストになった。

**正解**:

1. **値の出所＝型にする**: enum 値を代入するフィールドは、型注釈も同じ enum（`MessageFlags`）にする。`number` への暗黙の広がりは不整合のサイン。セルフレビュー時に「値と型のソースが一致しているか」を1項目として見る。
2. **判断の根拠を見える場所に残す**: 検討済みのトレードオフ（あえてこの順序/この設計にした理由）は、PR 説明文 or コードコメントに先回りで書く。書いておけばレビューアは settled として再指摘しない。「指摘されそうなこと」は脳内で潰すのではなく明文化する。
3. **コンテキストを変えてセルフレビューする**: コードを書いた同じ文脈のまま自己レビューすると、同じ思い込み（例: 上記の型不整合）を持ち越して見逃す。fresh-eyes パス（別エージェント/クリーンな文脈でのレビュー）を挟むと、型・一貫性の機械的な抜けを拾える。

## 2026-06-17: useCallback の deps に searchParams を入れ、effect 再実行リスクを作った（#134） [distilled]

**カテゴリ**: code-quality
**状況**: team_schedules で token/join のURL掃除時に team= を残すヘルパー `cleanUrlKeepingTeam` を `useCallback` で作り、`searchParams` を deps に入れた。そのヘルパーを `?token=` / `?join=` の useEffect の依存配列に含めた。
**ミス**: `useSearchParams()` の戻り値はクエリ変更時に同一性が変わるため、`cleanUrlKeepingTeam` の参照も変わり、依存する effect が再実行され得る。特に verifyMagicLink を含む token effect が pending 中に再実行されると二重呼び出しになる。既存コードは `token`/`joinToken` を**文字列に落として** deps にしており（searchParams オブジェクトを避ける流儀）、そこと不一致だった。
**正解**: effect/コールバックの deps には searchParams オブジェクトそのものを入れない。(1) 必要な値は文字列に派生させて deps にする、(2) 掃除系コールバックは呼び出し時点で `window.location.search` を読み、deps は安定参照（router）だけにする。「ガードフラグ(ref)」も、`router.replace` でクエリが消えれば次回 early-return する設計なら不要。
**なぜセルフレビューで見つからなかったか**: 自分の差分内（team= を残すロジック）の正しさは確認したが、**既存 effect の deps 設計の流儀（searchParams を避け文字列派生する）に揃っているか**という一貫性チェックを飛ばした。fresh-eyes エージェントが既存パターンとの差分として拾った。

## 2026-06-20: コメントに要素サイズの具体数値を書きすぎた（#155 / #156）

**カテゴリ**: code-quality
**状況**: スマホ時ヘッダー縮小・たたむトグルのコメントに、ヘッダー高さや要素サイズを px / Tailwind class（56px→44px、w-7/h-7、py-2=16px 等）で具体的に記述した。
**ミス**: 要素サイズの具体数値は (1) class を見れば分かる冗長情報で、(2) サイズ変更のたびにコメントが陳腐化して嘘になる。蒸留済み教訓「値に言及する必要が無いなら数値を書かない方が安全」と同根。
**正解**: 要素サイズ（高さ・幅・padding 等）は具体数値を書かず「スマホは一回り小さく / md以上は従来サイズ」のように定性的に書く。**例外**: 複雑な条件分岐・計算・非自明な相互依存（例: モーダル top-* がヘッダー高さに連動し、ログイン中/未ログインで高さが変わるため低い方に合わせる、という理由）は数値抜きでも説明を残す価値がある。
**なぜ起きたか**: 「コメント中の具体値はコードと一致させる」教訓を「だから正確な数値を書く」方向に適用したが、本来は「そもそも陳腐化する数値はコメントに書かない」が上位。値を書くか否かの判断を先に通すべきだった。

## 2026-06-20: PR マージ時に関連 issue を close し忘れる（毎回の取りこぼし）

**カテゴリ**: process
**状況**: PR #157（#153/#155/#156 を実装）をマージする際、ユーザーから「github の close ちゃんと使ってね」と指摘。PR 本文に `Closes #153` 等のキーワードが無く、さらに base が `develop`（デフォルトの `main` ではない）ため、マージしても issue が自動 close されない状態だった。
**ミス**: 実装で閉じられる issue があるのに、PR 本文に closing キーワードを入れず、マージ後の手動 close も忘れがち。ユーザー曰く「毎回のように忘れる」常習ミス。
**正解**: auto-close は **default ブランチ（`main`）向け PR でしか発火しない**。このリポジトリは feature→`develop`→`main` の運用なので:

- **feature→develop PR**: 完了させる issue を「**close予定**」として本文に**列挙**しておく（参照のみ。`Closes` は develop base では発火しないので使わない）。develop→main PR を組むときの拾い漏れ防止になる。
- **develop→main PR**: 束ねた close予定 issue を `Closes #N` で列挙 → main マージ時に auto-close（手動 close 不要）。
- **フォローアップとして新規起票した issue（例 #158）は列挙しない。**

**補足**: 今回は feature→develop PR の時点で手動 close したが、本来は「develop にいる間は open のまま追い、main PR で auto-close」が素直。
**仕組み化**: 「(1) feature→develop PR では close予定 issue を列挙、(2) develop→main PR では `Closes #N` で列挙」を運用ルール化。

## 2026-06-22: ユーザー入力を外部送信に埋め込む新経路で、メンション注入（@everyone ピング）をセルフレビューで見逃した（PR #181） [distilled]

**カテゴリ**: other（security/abuse）
**状況**: team_schedules 活動可能通知（#172）で、Discord Webhook の本文にメンバーの displayName や note（ユーザー入力）を埋め込んで送信する新経路を実装。セルフレビュー（fresh-eyes の review エージェント含む）で「問題なし」とした後、別レビューで指摘を受けた。
**ミス**: 送信ペイロードに `allowed_mentions` を指定しておらず、本文に `@everyone`/`@here` が混ざると送信先サーバー全員にピングが飛ぶ。表示名を `@everyone` にしたメンバーが1人いるだけで、通知のたびに巻き添えピングが発生する（相手も見る shared サーバーにも飛ぶため影響大）。
**正解**: ユーザー制御の文字列を新しい外部シンク（Discord/Slack/メール/HTML/SQL/シェル等）に流す経路を追加したら、**そのシンクが入力をどう解釈するか（既定でメンション/タグ/エスケープをどう扱うか）を確認し、安全側の既定を明示設定する**。Discord Webhook なら `allowed_mentions:{parse:[]}` でピングを全抑止。加えて**敵対的入力のテスト**（displayName=`@everyone` 等）を1件入れる。

**なぜセルフレビューで見つからなかったか**:

1. **レビューの観点に security/汚染データの lens が無かった**。correctness（latch・race・after・分岐網羅）と既存 lessons（コメント値一致・既存流儀との一貫性）に寄せて見ており、「このユーザー入力に最悪の値が入ったら外部で何が起きるか」を独立した検査項目にしていなかった。lessons.md にも security 系の蓄積が無く、観点に上がらなかった。
2. **害がシンク側の既定挙動に依存して可視化されない**。displayName は「ただの名前」に見え、害は Discord が content のメンションを既定でパースするという外部仕様で初めて顕在化する。diff を読むだけでは見えず、シンクの仕様知識＋ taint（displayName→content→送信）の追跡が要る。
3. **一貫性 lens がむしろ逆方向に働いた**。既存 `sendDiscordMessage`(discord/api.ts) も `allowed_mentions` 未指定で、「既存に合わせる＝正しい」と読めてしまう。だが本 PR は“任意の表示名を本文に埋める新経路”で危険度が違う。既存踏襲が常に安全とは限らない。
4. テストが benign な入力（"あ","い","う"）ばかりで、敵対的入力ケースが無く誤った安心感を補強した。

**回避可能性**: 完全に不可避ではない。「ユーザー制御の文字列 → 新規の外部シンク」を見たら taint/security の専用パスを通す、という lens を追加すれば検知できた種類。シンクの既定仕様（Discord はメンションを既定パース）を知らない場合でも、新規送信経路を足す時に公式ドキュメントの allowed_mentions/エスケープ既定を確認する習慣で補える。

## 2026-06-23: メンション注入対策を「自分の差分の新経路」だけに適用し、同じシンクの既存経路（公開募集メッセージ）を見落とした（PR #185） [distilled]

**カテゴリ**: other（security/abuse）
**状況**: `/team-schedule-invite` の参加フローに magic-link を足す PR #185 を自セルフレビューし「メンション注入の新経路なし＝安全」と結論。直後の別レビューで、同じ invite.ts 内の**公開募集メッセージ**（`buildRecruitContent` → `createFollowupMessage` / `safeEdit`）が `team.name`（管理者が任意設定のユーザー制御文字列）を本文に埋めつつ `allowed_mentions` 未指定で、`@everyone` を含むチーム名で公開チャンネルにピングし得ると指摘された。
**ミス**: 蒸留済み教訓 #181（ユーザー入力を外部シンクに流す経路は taint として扱い `allowed_mentions:{parse:[]}` を明示）を、**今回「自分が追加した行（magic-link）」にだけ**適用し、汚染チェックのスコープを diff の追加行に限定してしまった。同じ関数・同じ送信ヘルパーを使う既存の公開メッセージ（しかも ephemeral でなく public で危険度が高い）が taint レビューの対象から外れた。
**正解**: taint/security lens は「この PR で追加した行」ではなく「**この PR が触れている経路（関数・ファイル・送信ヘルパー）に流れるユーザー制御文字列すべて**」を対象にする。新経路を足すついでに、同じシンクへ既に流れている近傍の入力（同一関数内の team.name 等）も「最悪値で何が起きるか」を点検し、安全側の既定（`{parse:[]}`）に揃える。特に **public 送信は ephemeral より危険**（ephemeral はピングが飛ばない）なので優先度が高い。

**なぜセルフレビューで見つからなかったか**:

1. **taint レビューのスコープを「diff の追加行」に狭めた**。#181 で「新規の外部シンク経路を足したら taint を点検」と学んだが、それを「追加した文字列だけ」と解釈し、同じ関数が既に持っていた公開メッセージの team.name 埋め込みを「自分の変更ではない」と射程外にした。lessons #181 の「新規経路」は“自分の diff の行”ではなく“その変更が関与するシンク経路全体”の意味。
2. **ephemeral に気を取られ、public 経路の存在を背景化した**。新規追加分（magic-link）が ephemeral 限定で安全と確認できたことで安心し、同じファイルの public な募集メッセージへ注意が向かなかった。「秘匿性 OK」と「ピング抑止 OK」を混同した。
3. 前回 #181 と同様、敵対的入力テストが無く（今回は新規追加分の安全性のみ口頭確認）、`team.name=@everyone` を流す観点に至らなかった。

**仕組み化**: 「ユーザー制御文字列を外部シンクに送る変更」をレビューするときは、**diff の追加行ではなく、触れた送信関数に流入する全入力を列挙して**それぞれ最悪値を当てる。public/ephemeral を明示的に分類し、public は無条件で `allowed_mentions:{parse:[]}` 等の安全既定を要求する。対応する敵対的入力テストを1件足す。

## 2026-06-23: コメントとコードの「ギャップ」を許容してしまった — 正確化ではなく抽象化で潰すべきだった（PR #188 レビュー）

**カテゴリ**: code-quality
**状況**: PR #188（設定モーダルのタブバーが長いタブで潰れる不具合の修正）をレビュー。修正コメントが flex 潰れの前提を「高さ固定(モバイル `h-full` / PC `max-h-[90vh]`)」と書いていたが、PC のルートは実際には `md:h-auto`＋`md:max-h-[90vh]`（＝上限キャップであって固定ではない）。「軽微な指摘・任意」としてレビューで挙げた。
**ミス**: コメントとコードの間にギャップ（`md:h-auto` の存在で「固定」が不正確）があるのに、それを「軽微」と格下げして許容しかけた。ユーザーから「コメントのギャップはダメ。ギャップが起きるくらいなら、起きない粒度まで抽象化して」と指摘。
**正解**: コメントが実コードとズレうるなら、**ズレを「正確な値に直す」のではなく、そもそもズレが起きない粒度まで抽象化する**のが上位の解。具体的なクラス値・breakpoint 差・しきい値を列挙するほど、片方の変更で陳腐化する面が増える。今回は「高さ固定(h-full / max-h-[90vh])」→「高さに上限のある縦flexで自身がスクロールする構造」、「overflow-y-hidden」→「overflow-y(visible 以外)」に抽象化。潰れの**メカニズムの本質**（上限がある＋親がスクロール＋main軸の overflow が visible でない）だけ残せば、クラス値が変わってもコメントは真のまま。
**蒸留済み教訓との関係**: 「値に言及する必要が無いなら数値を書かない方が安全」(#155/#137 系)の延長線上。今回はさらに「ギャップの許容（軽微として見逃す）」自体が NG で、検知したら抽象化で根治する、という運用を明示。
**なぜ起きたか**: レビューで不一致を検知できていたのに、「実害なし・任意」と優先度を下げてユーザー判断に委ねた。検知した時点で「直すか否か」ではなく「ギャップが構造的に起きない書き方は何か」に進むべきだった。値の不一致は重大度で割引かない。
